## 问题与判据

要关闭的"待验证"是：**同一小文档生成 LaTeX/Typst 后，人工改动受支持结构能否可靠映射回语义图；
未知语法是否落成 `Raw` 且不丢内容。** 判据在动手前写定：

| # | 判据 |
|---|---|
| 1 | 无编辑 → 语义图不变，且再生成等于原文（定点） |
| 2 | 文本叶子局部改字 → 归因到该叶子，且再生成等于编辑后源码（往返） |
| 3 | 结构内部叶子改字 → 归因到内层叶子 |
| 4 | 整体换成受支持结构（`\sqrt{}` / `sqrt()`）→ 包裹成对应结构 |
| 5 | 未知语法 → 落成 `Raw`，**原文逐字保留**，且往返一致 |
| 6 | 跨节点编辑 → 冲突（拒绝猜测） |
| 7 | 括号不闭合 → 冲突（拒绝，不猜） |
| 8 | 增删行 → 冲突（明确不支持自动归因） |

## 环境

- 共享核心：`spikes/native-ui/core`（语义图 + 语义编辑 API）

## 方法与夹具

夹具是一份最小文档：段落（文本 `正文与 `）+ 独立公式（分数 `a/b`），两种方言各生成一遍。

调和采用**行 + 行内字节范围归因**：

1. 生成时记录每行属于哪个块级节点、行内各节点的字节范围，以及每个节点的**父位置**（父节点/槽位/下标）；
2. 编辑后按"最长公共前缀/后缀"找出每行内被替换的区间（字节偏移退到字符边界）；
3. 把区间归因给**完全包含它的最内层节点**；
4. 归因结果只有四类：文本替换、结构包裹、落成 `Raw`、冲突。

判据 5 的 `Raw` 落地方式是把文本叶子拆成 `[前缀][Raw][后缀]`：先为后缀新建文本节点、
再插入 `Raw` 节点、最后把原叶子裁剪成只剩前缀。这样**位置与原位置一致，内容一字不丢**。

## 结果

两种方言（LaTeX / Typst）各跑 8 个用例，**全部 PASS**；另有每行的"行映射自检"PASS。

```text
行映射自检：PASS（2 行）
  [PASS] 无编辑                → 语义图不变
  [PASS] 段落文本局部改字       → 节点 2 的 [6..6) → "以及"；往返一致
  [PASS] 结构内部叶子改字       → 节点 8 的 [1..1) → "b"；往返一致
  [PASS] 整体换成受支持结构     → 节点 8 包裹为 sqrt；往返一致
  [PASS] 未知语法              → 叶子 2 拆成 Text("") + Raw("\customcmd{正文}") + Text("与 ")
                               → 往返一致，原文逐字保留
  [PASS] 跨节点编辑             → 冲突（区间只覆盖结构节点的一部分）
  [PASS] 括号不闭合             → 冲突（拒绝）
  [PASS] 增删行                → 冲突（行数从 2 变为 3）
```

关键证据（`Raw` 不丢内容）：

```text
归因：叶子 2 的 [0..6) → Raw("\customcmd{正文}")
应用：拆分为前缀 + Raw("\customcmd{正文}") + 后缀
语义图：Document(Paragraph(Text(""),Raw("\customcmd{正文}"),Text("与 ")),Math(...))
再生成："\customcmd{正文}与 \n\[\frac{a}{b}\]\n"   ← 与人工编辑后的源码一致
```

## 失败与不确定性

必须说清楚这个 Pass 的边界——**支持面比听起来窄**：

- **一次只处理一处编辑。** 多处编辑、以及"编辑后又编辑回去"的组合没有验证。
- **不支持结构级重构。** 增删行、重排、在文本中间新建结构（例如把 `ab` 拆成 `a\sqrt{b}`）都不支持，
  一律报冲突。支持的结构编辑只有"把某个节点整体包裹成 `sqrt`/`frac`"这一种。
- **归因依赖行结构不变。** 任何重排或整体格式化都会让所有行错位 → 全部落成冲突。
  行为是安全的（不猜），但可用性有限。
- **诊断精度不足。** 判据 7（括号不闭合）被报成"结构节点不支持局部改写"，
  原因是区间落在结构节点内部；**诊断没有区分"不闭合"与"局部改写"**，用户看到的原因不是最直接的那个。
- **未覆盖**：真实文件监听与编码（BOM、CRLF）、并发编辑、大文档性能、
  多光标/批量替换、注释与空行、`Raw` 在重新生成时的转义边界。
- **未验证**：任何真实编辑器里的手工操作路径；本 spike 的"人工编辑"是程序构造的字符串替换。

## 对设计的影响

1. **核心需要原子的"拆分文本叶子"能力。** 本 spike 用 `InsertNode` + `InsertText` + `DeleteRange`
   手工拼出"前缀 + Raw + 后缀"，能work但脆弱（顺序、下标、失败回滚都是手写的）。
   建议给语义编辑 API 增加 `SplitText { node, at }` 与 `ReplaceRangeWithRaw { node, start, end }`，
   由核心保证原子性与撤销语义。这条应进 ADR 或模块文档。
2. **冲突是常态，不是异常。** 不支持的结构级改动必须走"人确认"的路径，
   而不是尝试自动归因。界面需要为冲突准备可读诊断与一键采用/放弃；诊断文案应指向最直接的原因。
3. **`Raw` 必须逐字保留**，这条已由本 spike 证实可做到（往返一致），应写成不变量。
