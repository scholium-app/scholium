# 2026-10-30：ubuntu-26.04 上 Ctrl+F1 窗口检查失败与 CI 换镜像

本记录只追溯这次 PR 查到了什么、改了什么、怎么验证的；CI 的现行约定见 [TESTING.md](../TESTING.md#8-ci-门禁)。
原始证据在 [evidence/ubuntu-2604-window](evidence/ubuntu-2604-window/)。

## 现象

GitHub 的 `ubuntu-latest` 在 2026-10-21 前后从 24.04 换成 26.04（runner provisioner 20261012 → 20261021）之后，
`spikes/typst-main-editor/chrome-check.py` 在两种界面语言下都停在第 8 步：第 7 步调整窗口大小之后，
`xdotool key --clearmodifiers ctrl+F1` 不再隐藏工具栏，`RuntimeError: timeout: toolbars hidden`，第 1–7 步全部通过
（[run 41086810562](https://github.com/scholium-app/scholium/actions/runs/41086810562)、
[run 41085133429](https://github.com/scholium-app/scholium/actions/runs/41085133429)）。
失败运行里应用最后一条 AUDIT 是 `toolbars_visible: true`，应用从未执行 `view.toolbars`
（[检查输出](evidence/ubuntu-2604-window/run-41086810562-chrome-en.log)、
[summary](evidence/ubuntu-2604-window/run-41086810562-chrome-en-summary.json)、
[最后一条 AUDIT 的 chrome facts](evidence/ubuntu-2604-window/run-41086810562-chrome-en-last-audit.json)）。
PR #65 先把 `rust.yml` 固定在 ubuntu-24.04。

## 排查

待验证的假设有四个：26.04 的 xkb 键位把 Ctrl+F1 映射成别的 keysym、xdotool 版本变化、`windowsize` 后丢失键盘焦点、
应用收到了按键但 egui 识别不同。

1. **两个镜像的软件版本。** xdotool 两边都是 `1:3.20160805.1`（26.04 只是重新构建），变化的是
   xkb-data 2.41 → 2.46、Xvfb 21.1.12 → 21.1.22、libxkbcommon 1.6 → 1.13。xdotool 升级的假设排除。
2. **不经过应用，直接看 X 服务器交付了什么。** 在私有 Xvfb `:97` 上开一个 `xev` 窗口并聚焦，发送同一条
   `xdotool key --clearmodifiers ctrl+F1`，记录 `xev` 收到的事件（脚本
   [repro-ctrl-f1.sh](evidence/ubuntu-2604-window/repro-ctrl-f1.sh)）。先在本机 podman 的 `ubuntu:24.04` / `ubuntu:26.04`
   容器里跑，再用临时诊断 workflow 在 GitHub 真实 runner 上跑
   （[run 41159889623](https://github.com/scholium-app/scholium/actions/runs/41159889623)），四份结果一致：
   - 24.04：`Control_L` 按下 → `F1` 按下（state 0x4，只有 Ctrl）→ 两键释放。
   - 26.04：`Control_L` 按下 → **`Alt_L` 按下** → Ctrl、Alt 释放 → 只有 `F1` 的**释放**，F1 的按下事件根本没有到达客户端。

   证据：[容器 24.04](evidence/ubuntu-2604-window/container-ubuntu-24.04.txt)、
   [容器 26.04](evidence/ubuntu-2604-window/container-ubuntu-26.04.txt)、
   [runner 24.04](evidence/ubuntu-2604-window/runner-ubuntu-24.04.txt)、
   [runner 26.04](evidence/ubuntu-2604-window/runner-ubuntu-26.04.txt)。
   这一步没有应用、也没有调整窗口大小，焦点前后都在 `xev` 窗口上，所以“`windowsize` 后丢焦点”和“egui 识别不同”
   两个假设都排除；失败只是恰好落在第 7 步之后，因为 `ctrl+F1` 是所有窗口检查里唯一的功能键组合。
3. **键位表差异。** 两个服务器上 F1（`<FK01>`，键码 67）都是 `CTRL+ALT` 类型，五级是
   `F1 F1 F1 F1 XF86Switch_VT_1`。差别在类型定义：xkb-data 2.46 给 `CTRL+ALT` 增加了大量显式条目，其中包括
   `map[Alt]= Level1` 和 `map[Control]= Level1`；2.41 的 `CTRL+ALT` 没有任何指向 Level1 的条目。对比两份键位表的全部类型，
   只有 `CTRL+ALT` 新增了 Level1 条目，而只有 F1–F12 用这个类型。
4. **xdotool 怎么选修饰键。** xdotool 3.20160805 的 `_xdo_populate_charcode_map` 对每个键码/组/级别，取类型里
   **第一个**指向该级别的有效条目的修饰键作为“产生这个 keysym 需要按的修饰键”，发送时在按键前把这些修饰键一起按下
   （`_xdo_send_key` → `_xdo_send_modifier`）。在 2.46 的键位表里，F1 的 Level1 第一个条目是 `map[Alt]`，于是
   `ctrl+F1` 实际发出的是 Ctrl+Alt+F1，也就是 Level5 的 `XF86Switch_VT_1`。这个 keysym 绑定的是服务器端的切换虚拟终端动作，
   按下事件被服务器自己消费掉（Xvfb 没有 VT 可切），只剩释放事件送到客户端。上游已经记录并修复了同一个问题：
   xdotool issue #491（xkeyboard-config 2.46 之后功能键被加上错误的修饰键），修复提交
   [15fc2fc5](https://github.com/jordansissel/xdotool/commit/15fc2fc55b8d60e46e9ba9099d71dadf1af67a64)、
   [107ea768](https://github.com/jordansissel/xdotool/commit/107ea768d1477eaf99200223179c57e4bfe67bc3)
   （提交说明正是“键码 67 加 Mod1Mask 也产生 F1，但程序收到的是 Alt+F1”）和
   [e354b69b](https://github.com/jordansissel/xdotool/commit/e354b69b858546e6bbcb7e117826337abf21e7e9)。
   本机 Arch 的 xdotool 4.20260303 已包含这些修复，所以本机（xkeyboard-config 2.48）一直通过；Ubuntu 26.04 仍是 2016 年的版本。

## 根因

Ubuntu 26.04 的 xkb-data 2.46 给功能键的 `CTRL+ALT` 类型加了 `map[Alt]= Level1`。Ubuntu 仍在用的 xdotool 3.20160805
据此认为产生 F1 要按 Alt，把 `ctrl+F1` 发成了 Ctrl+Alt+F1（`XF86Switch_VT_1`）。X 服务器把它当作切换 VT 的动作吞掉，
应用收不到 F1 按下。应用的按键处理没有问题：同一个键码 67 在 Ctrl 下送达时（真实键盘也是这样送达的），
26.04 上的应用照常切换工具栏（见下方验证）。

## 修复

修在测试驱动层，不动应用：

- `spikes/typst-main-editor/chrome_ui.py` 新增 `keycode(display, keysym)`，通过 libX11（`XKeysymToKeycode`，ctypes 调用，
  不增加依赖）从当前 X 服务器的键位表里查出 keysym 所在的键码。xdotool 对数字键码不推断修饰键，所以组合键里只有显式写出的修饰键。
- `chrome-check.py` 第 8 步改为 `ctrl+<F1 的键码>`。检查本身不变：仍然断言 Ctrl+F1 隐藏两条工具栏、菜单栏和标签栏保留，
  再由“视图”菜单恢复；没有放宽任何阈值或等待时间。
- `rust.yml`（lint、test）、`typst-fork.yml`（stock）都改为显式 `ubuntu-26.04`，注释改为“所有 workflow 固定同一个镜像，
  换镜像必须单独提 PR”。`docs.yml` 也从 `ubuntu-latest` 改为 `ubuntu-26.04`：它只跑一个 Python 链接检查，本身不怕换镜像，
  但三个 workflow 用同一个显式镜像，下次升级时一处搜索就能全部找到，不会有一个悄悄先变。
- apt 包名在 26.04 上全部存在（容器里 `apt-get install -s` 无报错），`install-ci-native-deps.sh` 与包列表不需要改。
- 临时诊断 workflow `diag-2604.yml` 只在排查时存在于分支上，提交前已删除；复现脚本作为证据保留。
- `docs/TESTING.md` 的 CI 段落写明固定镜像的约定，以及功能键组合要按键码发送。

## 验证

- 本机（Arch，xdotool 4.20260303，xkeyboard-config 2.48）：`python3 scripts/window-checks.py --only chrome --locale zh-Hans en`
  两种语言都通过（28.5 s / 28.7 s），说明按键码发送在新版 xdotool 上同样成立。
- 容器与真实 runner：`ctrl+67` 在 24.04 和 26.04 上都只交付 Ctrl 与 F1（state 0x4），见上面四份证据的第二段。
- `python3 scripts/check-doc-links.py` 通过。没有改 Rust 代码，Rust 门禁由 CI 执行。
- 26.04 上的完整 CI（lint、test 两种语言的全部窗口检查、stock 对照、文档链接）结果见下节。
